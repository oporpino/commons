# commons:infra

> **TLDR**: Infrastructure lives in `.infra/k8s/` (Kustomize) and `.infra/terraform/` (workspaces). Secrets are managed via ward — never SOPS. Terraform state lives in AWS S3. Database is Aurora Serverless v2. See `commons:database` for the full DB pattern.

## Repo isolation (CRITICAL)

Projects and the `infrastructure` repo are strictly isolated:

- **A project NEVER sees the `infrastructure` repo.** No reading its files, scripts, ward vaults, or paths — not in terraform, not in CI, not in helper scripts. A project's automation must work with the project repo alone.
- **`.infra/` is self-contained.** Everything the project's infra needs — terraform, k8s overlays, its own ward vault (`.ward/`), its own AWS account bootstrap (TerraformRole) — lives inside the project.
- **The `infrastructure` repo owns ONLY base and shared resources**: shared VPC/network, shared EKS cluster, shared messagebroker, org GitHub config, platform registry. Nothing app-specific lives there (no app vhosts, app DNS, app secrets).
- **The only sanctioned interface** between a project and shared infra is `terraform_remote_state` **outputs** (read-only contract over the state bucket). Never cross-reference repos by filesystem path or copy secrets between repo vaults at runtime.
- If a project needs a shared value (endpoint, account id, credential), it goes into the **project's own vault/config** during setup — populated by an operator, not read live from another repo.

## Secrets — ward (not SOPS)

Secrets are stored in **ward** vaults — never SOPS. Each project has its own ward vault at `.ward/`. The CI reads secrets via `ward exec <path> -- <command>`.

### Central vaults

Two shared vaults hold org-wide secrets and are the source of truth for bootstrapping any project:

**`bootstrap` repo (`.ward/vaults/bootstrap/`)** — one entry per project with `master_key` and `production_key` (Rails credentials). Also holds `commons.key` (the ward key for `.commons` itself) and any project-level env overrides (e.g. `messenger-api/env`, `trgclub-api/env`).

**`.commons` repo (`.ward/vaults/commons/`)** — shared infrastructure credentials:
- `commons.infra.eks_access_key` / `commons.infra.eks_secret_key` — AWS credentials for EKS access
- `commons.infra.eks_account_id` — shared account ID (616795656532)
- `commons.infra.eks_cluster_name` — `shared-kubernetes`
- `commons.infra.eks_region` — `us-east-1`
- `commons.infra.eks_role_arn` — TerraformRole ARN

When setting up a new project or machine, pull what you need from these two vaults — never recreate org-wide credentials from scratch.

**Ward vault structure per project:**

```
<app>              # shared across environments
  <app>.infra      # infra-level secrets (cloudflare, rails_master_key)
    staging        # per-environment (db password, ingress_hostname)
    production     # per-environment
```

**Which secrets go where:**

**DATABASE_URL is never in ward** — it's generated by terraform from RDS outputs. See `commons:database`.

## Environments

Always two workspaces: `staging` and `production`. Same terraform config, different state. Workspace drives:
- namespace: `<app>--<env>` (double hyphen separates app name from environment)
- domain: `<env>.<app>.ibft.app` (staging) / `<app>.ibft.app` (production)
- resource names: always include `${local.environment}` to avoid collisions

> **Namespace separator is `--` (double hyphen)** — this is the org standard so the app name and environment are visually distinct. The `ship.yml` in `ibft-corp/pipelines` generates `NAMESPACE: {app_name}--{environment}`. All projects must use this pattern.

## Resource naming — `<project>-<module>-<env>[-<role>]`

Every AWS resource (Name tag and identifier) follows one scheme, so diagrams read
cleanly and nothing is ambiguous:

```
<project>-<module>[-<sub>]-<env>[-<role>][-<index>]

Network (module-level, no sub):
     marketing-automation-production              (VPC)
     marketing-automation-production-public-0     (subnet)
     marketing-automation-production-private-1    (subnet)
     marketing-automation-production-nat          (NAT gateway)
     marketing-automation-production-igw          (internet gateway)
     marketing-automation-production-to-shared    (peering)

Primary resource of the module (the app itself — no sub):
     marketing-automation-production              (n8n DB cluster/instance base)
     marketing-automation-production-writer       (n8n DB instance)
     marketing-automation-cache-production        (n8n Valkey / Bull queue)

Secondary sub-resource (gets a <sub> to disambiguate):
     marketing-automation-leads-production-gentle-panda (leads DB instance)
     marketing-automation-leads-production-brave-otter  (leads DB instance)
```

**RDS instance names use a stable random suffix, not `-writer`/`-reader`** — Aurora
assigns the role at runtime, so the name must not claim it (see `@../skills/database/SKILL.md`).
Use `random_pet`. Other resources (subnets, NAT) keep descriptive role suffixes.

**The module's primary resource takes NO sub — it IS the module.** The `automation`
module is n8n, so the n8n database and cache are just `marketing-automation-*`;
adding `-n8n` would be redundant (n8n = automation). A **secondary** resource that
shares the module (like `leads`, a second database living inside automation) gets a
`<sub>` so its name shows it belongs to the module: `marketing-automation-leads-*`,
not the bare `marketing-leads-*` (which hid where it lives). Module-level network
resources (VPC, subnets, NAT) take no sub.

Rules:
- **No redundant account/qualifier words.** You are already in the module's account,
  so don't encode it. Bad: `marketing-mkt-*` (mkt = the marketing account = redundant).
  The base is `<project>-<module>-<env>`.
- **`<env>` comes before the role, not at the end.** `...-production-public-0`, not
  `...-public-0-production`. Groups all of an env's resources together when sorted.
- **Role suffix only where it disambiguates** — subnets (`public`/`private`), RDS
  instances (`writer`/`reader`), gateways (`nat`/`igw`), peering (`to-shared`). The
  VPC itself takes no role suffix (it's the base name).
- **public/private is a property of SUBNETS, not the VPC.** One VPC per env holds both
  public and private subnets; don't name the VPC "public" or "private".
- **No duplicate Name tags.** If two resources would share a Name, add the
  disambiguating role/index. Two VPCs (or anything) with the same Name in the console
  is a bug — either it's leftover junk to delete, or the name isn't specific enough.

## Be strict about VPCs and subnet groups — born-correct, zero leftovers

**This is a hard discipline, not a preference.** Getting VPC/CIDR/subnet-group
placement wrong is one of the most expensive mistakes in this codebase: it can only
be fixed by recreating the resource (snapshot → restore for databases), which means
downtime on production data and hours of rework. So be rigid and picky here, and
leave nothing behind:

- **Born correct.** A new VPC, subnet group, or DB cluster must be created in its
  final, standard shape from the very first apply — right CIDR (unique per env),
  right account VPC (never shared for app resources), right naming
  (`<project>-<module>[-<sub>]-<env>`, random instance names), right
  public/private split. Do NOT ship a "temporary" shape planning to fix it later;
  later means a recreate.
- **CIDR is forever.** Pick a unique, non-overlapping CIDR per peered VPC up front
  (staging `10.1`, production `10.2`, etc.). You cannot change it in place. Two
  peered VPCs sharing a CIDR is a silent routing bug (see the overlap rule below).
- **One subnet group's purpose is one thing.** Public-only for anything with a
  public instance (Looker reader); private-only for internal DBs/cache. Never mix
  public and private subnets in one group (Aurora will drop a public reader into a
  private subnet). If a cluster needs both a public reader and a private writer, the
  group is public-only and the writer stays private via `publicly_accessible=false`.
- **No leftovers, ever.** Every migration/rename that renames or recreates a
  resource MUST clean up what it replaced in the SAME work: delete `-old` clusters
  and instances, orphan subnet groups (RDS and ElastiCache), orphan security groups,
  detached VPCs, temporary snapshots, and the temporary terraform artifacts
  (`snapshot_identifier`, `-mkt` suffixes, migration locals). A half-cleaned account
  is how you end up hitting `VpcLimitExceeded` and `*AlreadyExists` on the next
  apply. If you delete via CLI, also reconcile the terraform state (`state rm`) so
  state == reality.
- **Verify clean at the end.** Finish by asserting zero residue: no `-old`, no
  `*-pre-*` snapshots, no `marketing-mkt-*`/legacy-named VPCs, and `terraform plan`
  shows no unexpected changes in every workspace.

## Per-account VPC + peering to shared (network architecture)

The org standard for multi-account networking:

- **Each account has its own VPC, peered to the shared VPC.** The shared VPC hosts
  the platform (EKS, messagebroker). Every other account (marketing, etc.) owns a
  VPC and reaches the platform — and is reached by it — over a VPC peering
  connection to shared. Cross-account resources talk over peering, on private IPs,
  never over the public internet.
- **App resources belong in the account's VPC, NOT the shared VPC.** The shared
  VPC is platform-only (EKS, messagebroker). An application's databases, caches,
  and workloads go in that app's account VPC — never dropped into the shared VPC
  "because EKS can reach them there." Putting an app DB in shared pollutes the
  platform VPC and, worse, co-locates staging and production in one VPC with no
  environment isolation. The EKS workload still reaches the app DB fine — over the
  peering, on private IPs. (Anti-pattern seen: the n8n `automation` cluster placed
  in the shared VPC for both envs; it should live in the marketing VPC like
  `leads` does.)
- **Private VPC by default.** By default an account's resources live in a private
  VPC (private subnets, egress via NAT, no inbound from the internet). This is the
  safe default: databases, workloads, internal services.
- **A separate public VPC only when something must be exposed.** When a specific
  resource genuinely needs public reachability (e.g. an Aurora reader for Looker
  Studio, a public endpoint), create/use a dedicated **public** VPC (public
  subnets + IGW) in that account for it — do not make the private VPC public. Keep
  the private-by-default VPC private and put only the intentionally-public resource
  in the public VPC. Guard the public resource with SSL + least-privilege auth, not
  by obscurity.
- Both the private and the public VPC in an account peer with shared, so the EKS
  workload reaches either over private IPs regardless of which one a resource is in.
- **Every peered VPC must have a UNIQUE, non-overlapping CIDR.** VPC peering does
  not work with overlapping CIDRs, and a route table can hold only one route per
  destination CIDR. If two VPCs that both peer with shared share a CIDR (e.g. mkt
  staging and mkt production both on `10.1.0.0/16`), the shared route table can
  only point `10.1.0.0/16` at one of the two peerings — traffic to the other
  becomes ambiguous and silently times out. Symptom seen: the public reader works
  (it goes via IGW, not peering) but the EKS→private-writer path times out for one
  environment. Allocate a distinct block per VPC up front (e.g. staging
  `10.1.0.0/16`, production `10.2.0.0/16`); fixing it later means re-CIDRing a VPC,
  which is a recreate.
- **NEVER mix inline `route {}` in `aws_route_table` with standalone `aws_route`
  for the same table.** An `aws_route_table` with inline `route {}` blocks becomes
  the *authoritative owner* of its entire route set: every `apply` deletes any
  route it doesn't see inline — silently including a peering/NAT route managed by a
  separate `aws_route`. Symptom: the return route (e.g. `10.0.0.0/16 → peering` on
  the public route table) keeps vanishing after each apply, so EKS→writer times out
  intermittently; `terraform plan` shows the `aws_route` as "will be created" every
  run even though state has it (drift). Fix: keep the `aws_route_table` with NO
  inline routes and declare ALL routes (IGW, NAT, peering) as standalone `aws_route`
  resources so they coexist. When converting an existing table, the inline default
  route already exists in AWS, so `terraform import aws_route.<name>
  <rtb-id>_0.0.0.0/0` before applying or you hit `RouteAlreadyExists`.
- **VPC Block Public Access (BPA) for defense in depth.** To guarantee private
  subnets (DB writer, cache, app DB) can never talk to the internet even if
  misconfigured with a public IP, set `aws_vpc_block_public_access_options` to
  `block-bidirectional` and add an `aws_vpc_block_public_access_exclusion` (mode
  `allow-bidirectional`) for each PUBLIC subnet (that needs the IGW: public reader,
  NAT gateway). BPA gates traffic via the IGW, so private-subnet egress via a NAT
  gateway (which lives in an excluded public subnet) keeps working — verify by
  `nc`-testing internet egress from a pod after applying. Each option/exclusion
  takes ~3-4 min to create.

This makes "public vs private" an explicit **choice of which VPC** — intentional,
reviewable, and hard to get wrong by accident. It is the same decision the section
below is about; here it is expressed at the account/VPC level.

## Placing resources in the right VPC (decide up front)

Which VPC a resource lands in is a design decision made at creation, and for some
resources it is effectively irreversible. **RDS/Aurora clusters cannot change VPC
in-place** — moving one means snapshot → restore (a risky window on prod data).
The same care applies to any resource whose network placement is baked in at
creation.

Before creating networked infra, decide the access model explicitly:

- **Public access needed** (Looker Studio, external SaaS, external colleague) →
  public subnets + IGW; keep writers private and expose only readers, guarded by
  SSL + a read-only user, not by hiding the resource.
- **Internal only** (EKS, apps in the VPC) → private subnets.
- **Staging and production must share the same VPC/topology.** Divergence means
  one env was created before the final terraform — fix it before there is data.

For the RDS/Aurora specifics (constraints, the snapshot→restore recipe, subnet
group vs security group name uniqueness), see `@../skills/database/SKILL.md`.

## Credential separation (CRITICAL)

`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` in the encrypted secrets file are **backend-only** — they authenticate to the S3 state bucket (`aws-shared-terraform-state` IAM user in the shared account). They must NOT be used for any AWS provider or resource operations.

All AWS provider operations (EC2, RDS, EKS, IAM, etc.) use `TF_VAR_aws_terraform_access_key_id` / `TF_VAR_aws_terraform_secret_access_key`, which assume the appropriate `TerraformRole` via `assume_role` in each provider block. Never route provider calls through `AWS_ACCESS_KEY_ID`.

## Provider configuration

### backend.tf — S3 backend (native AWS)

Use `skip_requesting_account_id = true` (not the deprecated `force_path_style`):

```hcl
terraform {
  backend "s3" {
    bucket  = "wehive-terraform-states"
    key     = "<project>/terraform.tfstate"
    region  = "us-east-1"
    encrypt = true
  }
}
```

`terraform_remote_state` data sources follow the same pattern — no custom endpoints, no skip flags. Credentials come from `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` injected by the encrypted secrets file.

### kubernetes provider

The k8s cluster token stored in remote state **expires**. Use the local kubeconfig (refreshed via `aws eks`) instead:

```hcl
provider "kubernetes" {
  config_path    = "~/.kube/config"
  config_context = "devops"
}
```

Refresh the kubeconfig before applying:
```bash
aws eks update-kubeconfig \
  --name shared-kubernetes \
  --region us-east-1 \
  --alias devops \
  --profile wehive-shared
```

**The token also expires mid-apply.** When one `terraform apply` both provisions a
slow AWS resource (RDS restore/replace takes 6–12 min) and then creates a
`kubernetes_job`/secret/etc., the k8s token minted at the start of the run can
expire before the k8s resource is reached — the apply fails late with
`Failed to create Job! API error: Unauthorized`. The AWS resources did apply; only
the trailing k8s step failed. Just re-run the apply (or `-target` the k8s
resource) with a fresh token. If it recurs, split slow DB work and k8s jobs into
separate applies.

### kustomization provider

The `kustomization` provider only accepts `kubeconfig_raw` — use `file()` to read the local kubeconfig:

```hcl
provider "kustomization" {
  kubeconfig_raw = file("~/.kube/config")
}
```

### rabbitmq provider

```hcl
provider "rabbitmq" {
  endpoint = "http://${data.terraform_remote_state.messagebroker.outputs.messagebroker_public_ip}"
  username = "admin"
  password = local.secrets["rabbitmq_admin_password"]
}
```

`rabbitmq_admin_password` must be present in the SOPS secrets file (same value across all projects).

## Variable priority (highest to lowest)

1. `TF_VAR_*` environment variables — override everything
2. SOPS secrets from `secrets/<env>.enc.yml` — static secrets
3. Dynamic terraform resource attributes — computed at apply time

The `wehive` wrapper loads SOPS first, then `TF_VAR_*` from the environment override them if present.

## Stateful resources (always protect)

```hcl
lifecycle { prevent_destroy = true }
```

Always on: `digitalocean_database_cluster` (PostgreSQL, Valkey/Redis). These survive `terraform destroy`.

## Apply creates everything from scratch

A `terraform apply` on a new workspace must create:
- Kubernetes namespace
- RabbitMQ vhost + user + permissions
- Kubernetes secret
- Cloudflare DNS record
- All k8s workloads via `kustomization_overlay`

Projects that manage their own stateful resources also create:
- DO managed database + cache clusters
- Database user, DB, firewall, grants (via kubernetes_job)

A `terraform destroy` removes all the above except stateful clusters (protected by `prevent_destroy`).

## Kubernetes / Kustomize

- Base manifests in `base/specs/` — environment-agnostic
- Overlays patch: ingress host/TLS, replica count, resource limits, image tag

## RBAC — Developer Access Profiles

Managed in `src/modules/kubernetes/rbac.tf` and `src/modules/kubernetes/providers/aws/iam-developer-roles.tf`.
Source of truth: `config/access.yml` — never edit terraform locals directly.

### Access model

| kubectl context | IAM role | Staging | Production |
|---|---|---|---|
| `wehive-<alias>-<app>--staging` | `eks-dev-<alias>` | full (admin) | — |
| `wehive-<alias>-<app>--production` | `eks-dev-<alias>` | — | read-only (member) or full+exec (owner) |
| `devops` | TerraformRole | full cluster | full cluster |

One context per namespace. Tokens expire in 15 minutes and auto-renew via `aws eks get-token`. Kubernetes RBAC groups (`developer-<project>-member`, `developer-<project>-owner`) control what each role can do inside each namespace.

**Namespaces are discovered dynamically** — any namespace ending in `--staging` or `--production` gets RoleBindings automatically via `for_each`.

### `config/access.yml` fields

```yaml
users:
  alias:
    github: github-username   # alias → GitHub username

devops:
  owners:
    - alias                   # full cluster access + CODEOWNERS on this repo
  repos:
    - infrastructure

projects:
  myproject:
    apps:
      - myproject-api         # drives namespace names and kubectl contexts
    members:
      - alias                 # staging full + production read-only
    owners:
      - alias                 # staging full + production full+exec + GitHub environment reviewer
```

### Adding a new project or user

Edit only `config/access.yml`. The `gen-access-tfvars.sh` script reads it and generates `access.auto.tfvars.json` before every terraform plan/apply — no manual sync with terraform locals needed.

```bash
# Edit config/access.yml, then:
make shared.kubernetes.plan   # generates tfvars + previews changes
make shared.kubernetes.apply  # creates IAM role, Access Entry, RoleBindings
```

After the apply, affected developers run `make k8s.init` to get new contexts.

### Developer setup

Prerequisites:
- `aws` CLI with profile `wehive-shared` configured (`~/.aws/config`) — assumes `TerraformRole` in the shared account (616795656532)
- `gh` CLI authenticated (`gh auth login`) — fetches `config/access.yml` from the infrastructure repo
- `yq` and `jq` — parse the access config and generate tfvars

```bash
make k8s.init
```

Creates one kubectl context per namespace the user has access to:
- `wehive-<alias>-<app>--staging` (green in summary — full access)
- `wehive-<alias>-<app>--production` (yellow in summary — readonly or exec depending on member/owner)
- `devops` (red — only for devops owners)

**Devops impersonation** — to test another user's access on your machine:
```bash
make k8s.init K8S_USER=matheus   # requires caller to be devops owner
```
Configures `wehive-matheus-*` contexts without touching your own `wehive-<alias>-*` contexts.

**After adding a new project or changing memberships** in `access.yml` → apply terraform → run `make k8s.init` to refresh contexts.

### When access.yml changes

1. PR to infrastructure adding/removing user or project membership
2. CI runs `gen-access-tfvars.sh` + `terraform plan` automatically
3. Merge → CI runs `terraform apply` → IAM Access Entry updated in EKS
4. Token expires in ≤15 min → next kubectl call picks up new permissions automatically
5. Developer runs `make k8s.init` only if new contexts need to be added to kubeconfig

## AWS account model

Every project has its own AWS account. The `infrastructure` repo manages the **shared account** only.

| Account | What lives here |
|---|---|
| `shared` (616795656532) | EKS cluster, shared VPC/network, shared messagebroker, ECR registry |
| `<project>` (e.g. onion: 675845727614) | Aurora/RDS, ElastiCache, S3 buckets, project-specific IAM, secrets |

**Rules:**
- Project-specific stateful resources (databases, caches, queues, storage) → **project account**
- Runtime infrastructure shared by multiple projects → **shared account**
- The shared EKS cluster runs pods from all projects — pods connect to their project account's resources
- Each project's `.infra/terraform/` bootstraps its own `TerraformRole` in its account and uses two AWS providers: `aws.shared` (for EKS data sources) and `aws` default (for project resources)

**Two providers pattern in `data.tf`:**
```hcl
# Shared account — only for EKS cluster auth
provider "aws" {
  alias      = "shared"
  region     = var.aws_region
  access_key = var.aws_terraform_access_key_id
  secret_key = var.aws_terraform_secret_access_key
  assume_role { role_arn = "arn:aws:iam::${var.aws_shared_account_id}:role/TerraformRole" }
}

# Project account — all project resources go here
provider "aws" {
  region     = var.aws_region
  access_key = var.aws_terraform_access_key_id
  secret_key = var.aws_terraform_secret_access_key
  assume_role { role_arn = "arn:aws:iam::${var.aws_account_id}:role/TerraformRole" }
}

data "aws_eks_cluster" "shared" {
  provider = aws.shared
  name     = "shared-kubernetes"
}
```

Required variables:
- `aws_shared_account_id` — shared account (616795656532), same for all projects
- `aws_account_id` — this project's account ID

## AWS resource naming convention

Pattern: `<app>-<type>-<env>` for logical groups; `<app>-<type>-<role>-<env>-<n>` for instances.

| Resource | Example |
|---|---|
| `aws_rds_cluster` | `onion-cluster-staging` |
| `aws_rds_cluster_instance` (writer) | `onion-cluster-writer-staging-1` |
| `aws_rds_cluster_instance` (reader) | `onion-cluster-reader-staging-1` |
| `aws_security_group` | `onion-aurora-sg-staging` |
| `aws_db_subnet_group` | `onion-aurora-subnets-staging` |
| `aws_elasticache_cluster` | `onion-cache-staging` |
| `aws_s3_bucket` | `onion-storage-staging` |

**Instance numbering starts at 1** (not 0) and is incremental when adding replicas.

## Naming convention — service vs app label

In k8s manifests, use `web` as the container/app name and resource name for the main web workload. Use the project name (e.g. `gateway`) only for external-facing resources like ingress hostnames, TLS secret names, namespace names, image names, and k8s secrets.

**Use `web` for:**
- `Deployment.metadata.name`
- `Deployment.spec.selector.matchLabels.app`
- `Deployment.spec.template.metadata.labels.app`
- `containers[].name`
- `Service.metadata.name` (the ClusterIP service)
- `Service.metadata.name` (the headless cluster service → `web-headless`)
- `HPA.metadata.name` and `scaleTargetRef.name`
- `ServiceMonitor.metadata.name` and its labels/selectors
- `CLUSTER_SERVICE` env var → `web-headless`
- Ingress `backend.service.name`
- `nginx.ingress.kubernetes.io/websocket-services` annotation

**Keep project name for:**
- Namespace (`<app>--<env>`)
- Ingress `metadata.name` (e.g. `gateway-proxy`, `gateway-admin`)
- Ingress hostnames and TLS secret names (e.g. `gateway-proxy-tls`)
- Image name (`616795656532.dkr.ecr.us-east-1.amazonaws.com/wehive/gateway`)
- Kubernetes secret name (`gateway-secrets`)
- `nodeSelector` / `tolerations` with `workload: <app>` — these are node labels, not pod labels
- Grafana dashboard metric queries (application-level labels)

## Database URL pattern

See `commons:database` for the full pattern — Aurora Serverless v2 + terraform-generated URLs.

**In `secrets.tf`** — URLs are built from RDS resource outputs:
```hcl
DATABASE_URL_READONLY   = "postgresql://...@${aws_rds_cluster.<app>.reader_endpoint}:.../db?sslmode=require"
DATABASE_URL_FULLACCESS = "postgresql://...@${aws_rds_cluster.<app>.endpoint}:.../db?sslmode=require"
```

**In k8s deployments** — all three env vars must be present:
```yaml
- name: DATABASE_URL
  valueFrom:
    secretKeyRef:
      name: <app>-secrets
      key: DATABASE_URL_READONLY  # safe default — entrypoint overrides at runtime
- name: DATABASE_URL_READONLY
  valueFrom:
    secretKeyRef:
      name: <app>-secrets
      key: DATABASE_URL_READONLY
- name: DATABASE_URL_FULLACCESS
  valueFrom:
    secretKeyRef:
      name: <app>-secrets
      key: DATABASE_URL_FULLACCESS
```

**Never store DATABASE_URL in ward** — it's derived from terraform RDS outputs.

**`deploy.staging` always rebuilds the image.** To apply only k8s manifests without rebuilding, use `kubectl apply -k .infra/k8s/overlays/staging` directly.

## Runtime mode pattern

The Dockerfile defines `ENTRYPOINT ["entrypoint"]` and `CMD ["run/runtime"]`. **Never set `command:` in k8s deployments** — it bypasses the entrypoint. The entrypoint handles DATABASE_URL injection before handing off to `run/runtime`.

`run/runtime` is implemented per-project and controls the process via `RUNTIME_MODE` env:

```sh
# web (default — no RUNTIME_MODE needed)
# worker → RUNTIME_MODE=worker
# habits → RUNTIME_MODE=habits
# beat   → RUNTIME_MODE=beat
```

In k8s deployments, only non-web workloads need to declare `RUNTIME_MODE`:
```yaml
# worker-deployment.yaml
env:
  - name: RUNTIME_MODE
    value: worker

# beat-deployment.yaml
env:
  - name: RUNTIME_MODE
    value: beat
```

Web deployment has no `command:` and no `RUNTIME_MODE` — the image default runs gunicorn.

## Ward keys — per-repo, unique, stored in 1Password (`tech | admin`)

Each repo has its own ward key stored in `.ward/.key` (never committed). Keys must be unique per repo — never share the same key across repos. All keys are saved in 1Password vault `tech | admin` under `WARD_KEY | <repo-name>`.

The `WARD_KEY` GitHub secret in each repo CI must match the key in `.ward/.key`.

**Rotating a ward key:**
1. Export all vault files: `ward export <file.ward> > /tmp/backup/<name>.yaml` for each `.ward` file
2. Delete `.ward/` and run `ward init` to generate a new key
3. Re-import each vault: iterate over yaml keys with `yq` and `ward set <path> <value>`
4. Commit the new encrypted vaults
5. Update 1Password and the repo's `WARD_KEY` GitHub secret

## Ingress

Every public-facing service needs a k8s Ingress with cert-manager TLS:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: <app>
  annotations:
    kubernetes.io/ingress.class: nginx
    cert-manager.io/cluster-issuer: letsencrypt-prod
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  tls:
    - hosts:
        - <host>.ibft.app
      secretName: <app>-tls
  rules:
    - host: <host>.ibft.app
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: <service>
                port:
                  number: 80
```

**Host is always a placeholder in `base/`** — overlays patch it per environment via `patches/ingress.yaml`.

## RUNTIME_MODE — web vs db processes

- **`RUNTIME_MODE=web`** — set on frontend/web deployments. Entrypoint skips DATABASE_URL injection and logs `[web] frontend process`.
- **`RUNTIME_MODE=worker`** — set on worker deployments. Entrypoint injects DATABASE_URL and runs worker process.
- **No `RUNTIME_MODE`** — default for Rails API. Entrypoint injects DATABASE_URL.

## Rules

- **Never fix infra problems manually** — always fix in terraform or kustomize
- Every resource name must include `${local.environment}` to be workspace-safe
- Always `plan` before `apply`
- **No SOPS** — secrets go in ward, never encrypted YAML files
- **No DATABASE_URL in ward** — always generated by terraform from RDS outputs
- Dynamic values (DB host, port, password) come from terraform resource attributes
- Static values (API tokens, master keys) go in ward
- Multi-module projects: one `.infra/` per module, separate terraform state keys
