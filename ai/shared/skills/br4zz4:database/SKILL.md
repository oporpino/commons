# commons:database

> **TLDR**: WeHive projects use Aurora PostgreSQL Serverless v2 managed by terraform. The RDS cluster is created in the shared VPC. Connection URLs are generated by terraform and injected into a `kubernetes_secret` — never stored in ward. The k8s secret is the only source of truth for database credentials at runtime.

## Pattern

Database infrastructure follows the messenger-api reference pattern:

1. **Terraform creates the RDS cluster** — Aurora PostgreSQL 17.4 Serverless v2 in the shared VPC
2. **Terraform creates the k8s secret** — `DATABASE_URL_READONLY` and `DATABASE_URL_FULLACCESS` are constructed from RDS outputs
3. **k8s deployment reads from the secret** — pods never receive credentials via environment or ward
4. **Ward does NOT hold DATABASE_URL** — it's a derived value, not a secret to be stored

## Terraform files

### `database.tf` — Aurora Serverless v2

```hcl
resource "aws_security_group" "aurora" {
  name   = "<app>-aurora-sg-${local.environment}"
  vpc_id = var.aws_shared_vpc_id

  ingress {
    from_port   = 5432
    to_port     = 5432
    protocol    = "tcp"
    cidr_blocks = [var.aws_shared_vpc_cidr]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_db_subnet_group" "aurora" {
  name       = "<app>-aurora-subnets-${local.environment}"
  subnet_ids = data.aws_subnets.shared.ids
}

resource "aws_rds_cluster" "<app>" {
  cluster_identifier     = "<app>-cluster-${local.environment}"
  engine                 = "aurora-postgresql"
  engine_mode            = "provisioned"
  engine_version         = "17.4"
  database_name          = "<app_snake>"
  master_username        = "<app_snake>"
  master_password        = var.aws_db_password
  db_subnet_group_name   = aws_db_subnet_group.aurora.name
  vpc_security_group_ids = [aws_security_group.aurora.id]
  skip_final_snapshot    = true
  deletion_protection    = false

  serverlessv2_scaling_configuration {
    min_capacity             = 0
    max_capacity             = 2
    seconds_until_auto_pause = 300
  }
}

resource "aws_rds_cluster_instance" "writer" {
  identifier           = "<app>-${local.environment}-writer"
  cluster_identifier   = aws_rds_cluster.<app>.id
  instance_class       = "db.serverless"
  engine               = aws_rds_cluster.<app>.engine
  engine_version       = aws_rds_cluster.<app>.engine_version
  db_subnet_group_name = aws_db_subnet_group.aurora.name
  publicly_accessible  = false
}
```

### `secrets.tf` — k8s secret with generated URLs

```hcl
resource "kubernetes_secret" "<app>" {
  metadata {
    name      = "<app>-secrets"
    namespace = kubernetes_namespace.<app>.metadata[0].name
  }

  data = {
    RAILS_MASTER_KEY = var.rails_master_key

    DATABASE_URL_READONLY   = "postgresql://${aws_rds_cluster.<app>.master_username}:${aws_rds_cluster.<app>.master_password}@${aws_rds_cluster.<app>.reader_endpoint}:${aws_rds_cluster.<app>.port}/${aws_rds_cluster.<app>.database_name}?sslmode=require"
    DATABASE_URL_FULLACCESS = "postgresql://${aws_rds_cluster.<app>.master_username}:${aws_rds_cluster.<app>.master_password}@${aws_rds_cluster.<app>.endpoint}:${aws_rds_cluster.<app>.port}/${aws_rds_cluster.<app>.database_name}?sslmode=require"
  }

  type = "Opaque"
}
```

### Ward keys needed

```
TF_VAR_aws_db_password      # random strong password — per environment
TF_VAR_aws_shared_vpc_id    # from shared infra
TF_VAR_aws_shared_vpc_cidr  # from shared infra
TF_VAR_rails_master_key     # from config/master.key
```

`aws_db_password` and `rails_master_key` go in the **per-environment** ward vault (`<app>.infra.staging`, `<app>.infra.production`). `aws_shared_vpc_id` and `aws_shared_vpc_cidr` go in the shared infra-level vault.

## k8s deployment — consuming the secret

```yaml
env:
  - name: RAILS_MASTER_KEY
    valueFrom:
      secretKeyRef:
        name: <app>-secrets
        key: RAILS_MASTER_KEY
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef:
        name: <app>-secrets
        key: DATABASE_URL_READONLY   # entrypoint overrides with FULLACCESS at runtime
  - name: DATABASE_URL_READONLY
    valueFrom:
      secretKeyRef:
        name: <app>-secrets
        key: DATABASE_URL_READONLY
  - name: DATABASE_URL_FULLACCESS
    valueFrom:
      secretKeyRef:
        name: <app>-secrets
        key: DATABASE_URL_FULLACCESS
```

The entrypoint (`commons/shell/tasks/docker/entrypoint.sh`) switches `DATABASE_URL` to `DATABASE_URL_FULLACCESS` when that var is non-empty. The deployment sets `DATABASE_URL` to the readonly value as a safe default.

## Choosing the VPC — decide up front, it's effectively irreversible

The VPC a cluster lives in is chosen at creation and **cannot be changed
in-place afterwards**. Two RDS/Aurora constraints combine:

1. All instances of a cluster share one DB subnet group, and a subnet group
   belongs to **exactly one VPC**. There is no writer-in-VPC-A + reader-in-VPC-B.
2. `ModifyDBSubnetGroup` refuses subnets from another VPC (`The new Subnets are
   not in the same Vpc as the existing subnet group`). Moving VPCs means
   **recreating** the cluster (snapshot → restore), a risky window on prod data.

So before creating a cluster, decide the access model:

- **Needs public access** (Looker Studio, external SaaS/tool, a colleague) →
  public subnets + IGW. Keep the writer `publicly_accessible = false` and only the
  reader `true`; the guard is enforced SSL (`rds.force_ssl`) + a read-only role,
  not hiding the DB.
- **Internal only** (EKS, apps in the VPC) → private subnets.
- **Staging and production must be born in the same VPC / topology.** Divergence
  between envs means one was created before the final terraform — fix it while
  there's no data (cheap); later it's snapshot/restore.

VPC-migration recipe (when you must move an existing cluster): snapshot → rename
old cluster/instances to `-old` (frees the names) → add temporary
`snapshot_identifier` + `lifecycle { ignore_changes = [master_password,
snapshot_identifier] }` (master password comes from the snapshot; do NOT
regenerate the `random_password`) → `terraform state rm` the old resources
(preserve the `random_password`) → `apply` to recreate from the snapshot in the
right VPC → validate → drop `-old` and remove `snapshot_identifier`. Note: a DB
subnet group name is unique per account/region (not per VPC), so the new subnet
group needs a distinct name while `-old` coexists (e.g. a `-mkt` suffix); a
security group name is unique per VPC, so it does not collide across VPCs.

For the broader "pick the VPC up front" guidance across all networked infra (not
just databases), see `@../skills/infra/SKILL.md`.

## Rules

- **NEVER encode writer/reader in the instance name — use a stable RANDOM name.** Aurora assigns the writer/reader role at runtime by promotion tier, not by the `identifier`. A `-reader` instance can be promoted to writer on failover or recreation, and then the name lies (the console shows the `-reader`-named instance as "Writer instance"). Instead give each instance a neutral, stable random suffix and read the real role from the cluster at runtime. Use the terraform `random` provider's `random_pet` (already in the stack for `random_password`): `identifier = "<app>-<env>-${random_pet.x.id}"` → e.g. `marketing-automation-leads-production-gentle-panda`. Bad: `marketing-automation-production-1` (ordinal) AND `...-reader`/`...-writer` (lies on failover). Good: `...-gentle-panda`, `...-brave-otter`. Control which instance is public (Looker) via `publicly_accessible` and which stays reader via `promotion_tier` — never via the name.
- **`promotion_tier` does NOT decide the writer at create-time — pin it.** When a public reader must NOT be the writer (e.g. leads: public reader for Looker, private writer), `promotion_tier` alone is not enough. `promotion_tier` only governs *automatic failover* (which reader gets promoted when the writer dies); it does **not** control which instance Aurora picks as the writer on the *initial create*. So when both instances come up together (any recreation), Aurora can make the `publicly_accessible = true` tier-15 instance the writer — exposing the writer publicly and hiding the reader from Looker. The symptom is a silent inversion after every instance recreation. Fix: pin the writer deterministically with a `null_resource` + `local-exec` that runs `aws rds failover-db-cluster --target-db-instance-identifier <private-tier-0-instance>` on any change to the instance identifiers (trigger on both instance ids). It is idempotent — a no-op when the private instance is already the writer. Do NOT rely on manual post-apply failover; you (or CI) will forget it and the writer will be exposed. Wait for `db-instance-available` before the failover so it doesn't race the instance coming up, and — because failover is **async** — poll `describe-db-clusters` until the target actually becomes the writer before the provisioner returns (fail the apply if it doesn't converge). Otherwise the apply finishes mid-flip and a follow-up `describe` still shows the old (inverted) writer, which looks like the pin failed when it just hadn't propagated yet.

  Simpler alternative if the writer does not need to be private: make **both** instances `publicly_accessible = true` and let Looker use the `reader_endpoint` (`cluster-ro-...`) — it always routes to a reader regardless of failover, and write protection comes from the read-only `looker` role + SSL, not from hiding the writer. Then no pin is needed. Choose the pin only when you want the smaller attack surface of a writer that doesn't answer publicly at all.
- **Changing `identifier` forces replacement — and hits every env.** Editing an instance's `identifier` in terraform destroys and recreates the instance (downtime), and because the name is built from `${local.environment}`, the change lands on staging AND production. To rename without a replace: rename the instance in the AWS console/CLI first (`modify-db-instance --new-db-instance-identifier`, per env), then `terraform state rm` + `terraform import` the new id. Never let `terraform apply` do an identifier rename on a database you care about.
- **Applying a cluster parameter group briefly destabilizes the cluster.** Setting `db_cluster_parameter_group_name` (e.g. to force SSL) reboots/reconfigures the cluster; for a few minutes connections time out even though the SG and routes are fine. A `kubernetes_job` that runs psql (like `leads_db_setup`) will fail in that window — it is transient, not a real network problem. Wait for the instances to report `ParameterApplyStatus: in-sync` and `available`, then re-run the job. Don't chase phantom SG/peering bugs during the reboot window.
- **NEVER mix public and private subnets in one DB subnet group.** A cluster has exactly one subnet group, and Aurora places each instance in a random subnet from it. If the group mixes public and private subnets, a `publicly_accessible = true` reader can land in a *private* subnet (no IGW route) → it gets a public IP but is unreachable from the internet (timeout). Symptom: the reader endpoint resolves to a public IP but times out; its ENI is in a `*-private-*` subnet. Fix: the subnet group holds **only public subnets**. A "private" writer stays private via `publicly_accessible = false` — it's reachable from inside/peering on its private IP regardless of the subnet being public. So: public-only subnet group + `publicly_accessible` per instance (reader true, writer false). Put genuinely-private resources (app DB with no public reader, cache) in a separate private-subnet group.
- **On Aurora, `DROP ROLE`/`DROP OWNED`/`REASSIGN OWNED` needs role membership first.** The Aurora master user is `rds_superuser`, NOT a real superuser, so it cannot drop a role that still holds privileges/objects unless it is a *member* of that role. To retire a login role (e.g. rename `looker` → `reader`): `GRANT looker TO postgres; REASSIGN OWNED BY looker TO <owner>; DROP OWNED BY looker; DROP ROLE looker;` — all in one `DO` block guarded by `IF EXISTS`. Skipping the `GRANT ... TO postgres` yields a silent `permission denied` that fails the setup job with `ON_ERROR_STOP=1`. `DROP OWNED BY` clears *all* privileges the role was granted across every schema in one shot — don't hand-`REVOKE` schema by schema.
- **Grant a read-only role across ALL user schemas, not just `public`.** A BI reader (Looker) must see every data schema (`public`, `latam`, `performance`, …). Loop over them in SQL instead of hardcoding `public`: `DO $$ DECLARE s text; BEGIN FOR s IN SELECT nspname FROM pg_namespace WHERE nspname NOT LIKE 'pg_%' AND nspname <> 'information_schema' LOOP EXECUTE format('GRANT USAGE ON SCHEMA %I TO reader', s); EXECUTE format('GRANT SELECT ON ALL TABLES IN SCHEMA %I TO reader', s); EXECUTE format('ALTER DEFAULT PRIVILEGES FOR ROLE <owner> IN SCHEMA %I GRANT SELECT ON TABLES TO reader', s); END LOOP; END $$;`. The `ALTER DEFAULT PRIVILEGES` line is what keeps *future* tables readable.
- **A `kubernetes_job` that fails deletes its pod immediately — bump `ttl_seconds_after_finished` to debug.** With `wait_for_completion = true`, terraform removes the failed job on apply error, so `kubectl logs` finds nothing (ttl 60 races you too). Temporarily raise `ttl_seconds_after_finished` to 600, re-apply, read the logs, then revert. Or reproduce the SQL directly: read-only checks (does the role exist? is `postgres` a member? does the role own objects?) run fine against the public reader endpoint without touching the writer.
- **Looker Studio SSL: use the REGIONAL RDS CA bundle, not the global one.** Looker validates the server cert; upload the CA in its "Server certificate" field. The global bundle (`truststore.pki.rds.amazonaws.com/global/global-bundle.pem`, ~108 certs) can make Looker hang ("context deadline exceeded" / stuck loading) — use the small regional bundle (`.../us-east-1/us-east-1-bundle.pem`, 3 certs). The cluster endpoints (`cluster-...`, `cluster-ro-...`) ARE in the instance cert's SANs, so `sslmode=verify-full` passes; test with `PGSSLROOTCERT=<bundle> psql "...sslmode=verify-full"` before blaming the cert. Since `rds.force_ssl=1` is cluster-wide, you cannot exempt a single user from SSL — either supply the cert or drop `force_ssl`.
- **Never store DATABASE_URL in ward** — it's generated by terraform from RDS outputs
- **Always use Aurora Serverless v2** — `db.serverless` instance class, `min_capacity=0` for cost
- **`skip_final_snapshot=true`** in staging only — set `deletion_protection=true` in production
- **Security group restricts to VPC CIDR** — never expose RDS publicly
- **`DATABASE_URL_READONLY` and `DATABASE_URL_FULLACCESS` always both present** — deployments use readonly, migrations and console use fullaccess
- **`RUNTIME_MODE=worker`** on worker deployment — entrypoint handles DB mode switching
- For web/frontend processes — set `RUNTIME_MODE=web` so entrypoint skips DB injection entirely
